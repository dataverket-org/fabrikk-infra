# Plan: an S3 service in the cluster, `dataverket.s3.osl1.dvkt.no`

Written 2026-10-04. Nothing is applied. `docs/storage.md` says an in-cluster S3 endpoint comes with its first writer,
in a plan of its own; this is that plan. Step 1 is the gateway, with object lock available. Step 2 is research and
a plan for Zitadel as its identity provider, in the way the rest of the platform does it (decision 015).

## Why

Three workloads want an S3 endpoint inside the cluster: Zulip's uploads and avatars when Zulip comes, Forgejo's LFS,
attachments, packages and Actions artifacts, which today live on the `gitea-shared-storage` volume, and whatever
Dataverket's own services store next. The hov1 site is the backup target (decision 020), reached by address over the
public internet, and is the wrong place for data a service reads on every request.

versitygw is already the S3 implementation Dataverket runs and has a swamp extension for, `@dataverket/versitygw`,
and `backup/versitygw/` holds the operational knowledge: one account per writer, owner of one bucket, nothing else.
Running the same software in the cluster means one S3 vocabulary, one set of runbooks and one extension.

## Goals

1. **One endpoint, named**: `https://dataverket.s3.osl1.dvkt.no`, path-style, region `us-east-1`, Let's Encrypt
   through the gateway, with the in-cluster writers reaching it by Service name (decision 013's shape) and browsers
   by the public name. Read right to left the name is zone, site, service, org: `osl1` is the site, as `hov1` is a
   site, and `dataverket` is the org, the leftmost label so that one wildcard, `*.s3.osl1.dvkt.no`, covers every
   org's gateway when there is more than one (see "One gateway per org" below). The bare `s3.osl1.dvkt.no` is
   reserved and never a tenant's endpoint.
2. **The posix backend on one Cinder volume.** Buckets are directories, objects are files, metadata in xattrs. The
   volume is one redundancy layer (decision 018); the off-provider copy is the hov1 site (020).
3. **Object lock available.** The gateway is started so that a bucket can be created with object lock and, with it,
   versioning. Which buckets get it is each writer's choice at creation.
4. **The hov1 model of accounts, until step 2**: one account per writer, `user` role, owner of its bucket; the root
   key pair is read by nothing unattended, and no secret is ever in an argument, a data record or a log line.
5. **Read through swamp**: a model `osl1-s3` of type `@dataverket/versitygw/gateway`, the same `inventory` and
   `check` that read hov1.
6. **Backed up to the hov1 site**, as a directory tree, with a written restore.

## What versitygw 1.8.0 gives us, checked 2026-10-04

Read from the wiki and the v1.8.0 source, not from memory. The hov1 site runs this version.

| Fact | Consequence for this plan |
|---|---|
| Object lock works on the posix backend. Lock state, retention and legal hold are xattrs on the bucket directory and on the object | Backup must carry xattrs, or the restore re-puts the lock configuration |
| A bucket created with `ObjectLockEnabledForBucket` gets versioning enabled at once, when the gateway has a `--versioning-dir`; without one, lock is allowed on an unversioned bucket, and a locked object cannot be overwritten at all | Run the gateway with a versioning directory, so lock-enabled buckets behave as S3 clients expect |
| `COMPLIANCE` retention cannot be shortened or removed by anyone, root included. `GOVERNANCE` can be bypassed with the header by root, or by a user granted `s3:BypassGovernanceRetention`; overwriting a governance-locked object needs that grant from everyone, root too | Compliance mode is a real commitment on a volume no one can trim; governance mode is the sane default |
| Lifecycle configuration is "recognized but not implemented": `PutBucketLifecycleConfiguration` answers `NotImplemented` | A versioned bucket keeps every non-current version until a client deletes it by version id. Retention is the writer's job, as on hov1 |
| The versioning directory must be outside the gateway root; the Helm chart mounts data, versions, sidecar metadata and the internal IAM store as four `subPath`s of one claim | One Cinder volume holds everything, which is what we want |
| Internal IAM (`--iam-dir`) stores accounts in a plaintext `users.json`; accounts are made over the admin API, SigV4-signed by root | Same as hov1; the admin port stays inside the cluster |
| Startup tests xattr support on the gateway root and refuses to start without it | ext4 on Cinder has xattrs; the test is the proof |
| The Helm chart (`chart/`, 0.4.1 in the v1.8.0 tag, published as `oci://ghcr.io/versity/versitygw/charts/versitygw`) runs non-root, read-only root filesystem, one replica, `RollingUpdate` by default | On a `ReadWriteOnce` volume the strategy must be `Recreate`, set at install: a live Deployment cannot switch strategy through Flux |
| `aws:SourceIp` in a bucket policy is the connection's peer, never `X-Forwarded-For` | Behind Envoy every client is Envoy; no IP conditions in bucket policies |
| A standalone IAM service (`versitygw iam`) exists, with IAM users, roles, inline policies, OIDC providers and `AssumeRoleWithWebIdentity` | Step 2's mechanism; detailed below |

## Step 1: the gateway

### Shape

| Piece | Choice |
|---|---|
| Namespace, Service | `versitygw`, `versitygw.versitygw.svc.cluster.local:7070`, plain HTTP inside the cluster |
| Delivery | Gitless, as zot (decisions 011 and 012, README "Gitless delivery"): `artifacts/versitygw/` is the authored directory, plain manifests with the image pinned by digest, pushed as the OCI artifact `platform/versitygw-config` into zot by its `push.sh`; `apps/versitygw/source.yaml` is the `OCIRepository` on the Service name and the Kustomization that applies it with the cluster key. The chart was read for what the gateway needs and not used: five objects do not need Helm |
| Volume | One PVC, `csi-cinder-standard-retain`, 20 GB to start, expandable online. `Retain`, because the data is not rebuildable. Standard tier: uploads and LFS are throughput, not IOPS; SSD is one line to change if the measurement says otherwise |
| Backend flags | `posix /mnt/data`, `--versioning-dir /mnt/versioning`, `--iam-dir /mnt/iam`, region `us-east-1` |
| Root key pair | A sops-encrypted Secret in `apps/versitygw/`, born as a cluster file; the chart reads it by `auth.existingSecret`. A person copies it into `vaults/operator/osl1/root.enc.json` for the swamp model (decision 016, operator rule 3) |
| Public name | A new listener on `envoy-gateway` for `*.s3.osl1.dvkt.no` with a wildcard certificate from `letsencrypt-prod`, and an `HTTPRoute` for `dataverket.s3.osl1.dvkt.no` in `apps/versitygw/`. Path-style only: a virtual-host bucket name would land two labels under the wildcard and fail on the certificate, which is the intended loud failure; clients are configured path-style, not left on auto |
| Admin API | Port 7071 on its own Service, `versitygw-admin`, ClusterIP only, never a route. Reached from the swamp host through `kubectl port-forward`, opened by a task |
| Replicas | 1, a StatefulSet with a `volumeClaimTemplate`: a StatefulSet never runs two pods for one ordinal, so the `ReadWriteOnce` volume cannot wedge a rollout, which a Deployment needs `Recreate` for |
| Policy | None yet, as zot has none; the admin API is SigV4-signed by root, and a NetworkPolicy for the two Services is a follow-up |

The Zitadel-shaped question of where in-cluster writers point: Forgejo points at the Service, plain HTTP, `SERVE_DIRECT`
off, so its users never see the S3 endpoint. Zulip generates presigned URLs that browsers fetch, so Zulip points at
the public name over TLS, and its avatar bucket carries the world-readable policy Zulip documents.

## One gateway per org

Discussed 2026-10-04 against the tenants model in `kode/fabrikk` (`docs/explanation/sentral.md`): a tenant is a Zitadel
organisation, a service is a Zitadel project the operator org owns and grants to tenant orgs, roles are assigned per
user by the tenant admin, the token is a JWT access token whose audience is the project id and whose resourceowner
claim is the tenant. Two ways to serve that with S3 were compared; the comparison is recorded here so step 2 does not
redo it.

| | One versitygw per org, on one Cinder volume each | One radosgw for every org |
|---|---|---|
| Tenant boundary | The deployment: bucket namespace, `ListBuckets`, IAM store and root key are per org by construction | RGW tenants and accounts: separate bucket and identity namespaces inside one gateway |
| Identity | A template: every gateway registers Zitadel once with the project's client id, its trust policies pin the resourceowner claim to the one org id, the roles are the project's roles. Onboarding renders the same manifests with a new org id | Session tags from the token (`https://aws.amazon.com/tags`) become `aws:PrincipalTag`; one role set and one policy, `s3:ResourceTag/tenant` equals `aws:PrincipalTag/tenant`, serve every org |
| Claims | Top-level scalar and array claims only; Zitadel's nested roles claim is dropped, a flat claim from an action is needed | Every claim, recursively, but an object is flattened to its inner keys and loses the role name; the same flat claim or the tags claim is needed |
| Quota and redundancy | The volume is the quota; Cinder's three copies are the layer (018) | RGW quotas; Ceph's replication or erasure coding |
| What it needs | Nothing the cluster lacks | Ceph, which is not a Cinder volume and fits the bare-metal direction, not today's cluster |
| Missing | Lifecycle rules; each gateway is `ReadWriteOnce` and pinned to one worker, and Nova caps volumes per instance, so tenants per worker has a ceiling to check | Nothing of the above; the blast radius of an upgrade is every tenant |

The reading: the per-org versitygw is the shared-nothing shape the tenants model already uses, one org, one NATS
account, one gateway, and it makes the identity work a template. radosgw is the answer when the number of tenants or
the volume of data makes N pinned gateways silly, or when bare metal makes Ceph the storage anyway. Moving a tenant is
an S3 to S3 copy. In fabrikk's terms Objekt's downstream port gets two adapters, and the osl1 gateway in this plan is
the first instance of the per-org shape, with Dataverket itself as the org.

**Envoy keeps one endpoint.** One listener, one wildcard certificate and one Gateway front every org's gateway, but
the request has to carry the org in a field SigV4 signs as sent and that anonymous requests also carry. That is the
hostname, hence `<org>.s3.osl1.dvkt.no`, and `<org>.iam.osl1.dvkt.no` for the IAM and STS endpoint, whose
`AssumeRoleWithWebIdentity` names the role in the POST body where Envoy cannot route on it. What does not work: a path
prefix per org, since the first path segment is the bucket and the client signed the path it sent; routing on the
credential, since STS keys carry no org and anonymous requests carry none; inspecting the identity, since S3 requests
carry a signature, not a token. The fallback if a bare hostname is ever a product requirement is a route per bucket on
`s3.osl1.dvkt.no`, matched by path prefix without rewrite, at the cost of a global bucket namespace and a route table
the product maintains.

**The org label** is a slug fixed at onboarding and recorded with the Zitadel org id; the id is stable but long, the
name can change. `dataverket` is the first.

## Step 2: Zitadel as the identity provider, research

Not applied, and not applied before step 1 has run for a while. This section records what was found so the plan can
be written against it.

### The mechanism versitygw offers

versitygw 1.8.0 has two unrelated identity models. The built-in backends (internal, LDAP, Vault, FreeIPA, S3) are
account directories with a role tier per account and no policy language. The **standalone IAM service**
(`versitygw iam`) is a separate process speaking the AWS IAM and STS Query API: IAM users with up to two access keys,
IAM roles with trust policies, inline identity policies, OpenID Connect providers, and `AssumeRoleWithWebIdentity`.
The gateway connects to it over a private endpoint (unix socket or mutual TLS; the chart can issue the
certificates through cert-manager), asks it to derive signing keys and evaluate policies, and holds no secret itself.
The two are mutually exclusive on one gateway and share no data: moving to standalone IAM recreates every account.

The federation flow:

1. An OIDC provider is registered once with its issuer URL and the client ids it accepts, here
   `https://zitadel.dataverket.org` and the client id of a Zitadel application made for S3. The service fetches
   the discovery document and JWKS from the issuer at assume time and caches keys five minutes.
2. A role carries a trust policy: `Principal.Federated` is the provider, the action is
   `sts:AssumeRoleWithWebIdentity`, and conditions scope `zitadel.dataverket.org:aud`, `zitadel.dataverket.org:sub`
   and any other top-level scalar or scalar-array claim of the token. Nested object claims are dropped, so Zitadel's
   default `urn:zitadel:iam:org:project:roles` claim, an object, is not usable as a condition. A Zitadel action that
   adds a flat `groups` array claim to the token makes `ForAnyValue:StringEquals` on it work.
3. A caller presents a Zitadel ID token and gets credentials that live 900 to 43200 seconds, capped by the role's
   `MaxSessionDuration`. The gateway resolves the session token through the private endpoint on every request;
   deleting a key or a role takes effect on the next request.
4. The role's inline policy says which buckets and actions, in AWS policy grammar: `s3:ListBucket`, `s3:GetObject`
   and so on against `arn:aws:s3:::<bucket>` and `arn:aws:s3:::<bucket>/*`.

### How that fits decision 001 and 015

- A person authenticates in the browser as themselves, through the device flow `task admin:zitadel-key` already
  drives, exchanges the ID token for S3 credentials that expire, and the AWS CLI reads them through a
  `credential_process` entry in `~/.aws/config` that names a profile and no credential. Tier 2 as 001 defines it, and
  the same pattern decision 015 gives Kubernetes.
- Automation is a Zitadel service user whose token is a JWT the project issues (the application set to JWT access
  tokens), assuming a role of its own, named per purpose, so both Zitadel's log and the gateway's access log say
  which one acted. An in-cluster writer such as Forgejo has no OIDC client in it, so it keeps a long-term IAM user
  with one access key and an inline policy on its bucket, the tier 3 item it is today, rotated by `aws iam
  create-access-key` and `delete-access-key` without downtime, which the internal backend cannot do.
- Authorization moves into policy documents in git, applied by swamp, as 015 moves RBAC into ClusterRoleBindings.
  The one-account-one-bucket rule becomes an inline policy per user or role, which `check` evaluates from the IAM
  API instead of from the admin API's ownership listing.

### What changes, and what it costs

| Today, internal IAM | Under standalone IAM |
|---|---|
| Every bucket owned by its writer's account | Every bucket owned by root; a user's access is its identity policy. `ListBuckets` shows every bucket to anyone granted `s3:ListAllMyBuckets` |
| Accounts over the admin API; `accounts` and `check` in the extension read it | `create-user`, `list-users`, `change-bucket-owner` answer 501; the extension needs IAM-API methods, and `check`'s ownership rule is replaced by a policy rule |
| One process | Two processes, two root credentials or one shared, mutual TLS between them, and a second plaintext store, `iam.json`, holding every user's secret key and the live STS sessions |
| The gateway keeps serving if nothing else runs | The gateway fails closed when the IAM service is unreachable: `InternalError` on every request |
| `userplus` can create buckets | Only `s3:CreateBucket` in a policy does |

The file store coordinates writers inside one process, so the IAM service is one replica forever unless it is given
Vault as its store, which Dataverket does not run.

### What the step 2 plan must settle

1. **Whether the gain is worth two processes.** Humans reaching S3 with expiring credentials from a browser login
   is the gain. If the only human use is the operator's `inventory` and `check`, which root signs today, there is no
   human to federate yet, and the plan waits for one. Zulip's and Forgejo's users never touch S3 directly.
2. **The claim.** A Zitadel action that writes a flat `groups` claim, or roles asserted per application in the
   token in a flat shape, verified against a throwaway Zitadel with the `@dataverket/zitadel` smoke setup, before
   any trust policy is written against it.
3. **Session lifetime**, the same question 015 leaves open for the refresh token: the ID token lives minutes, the
   STS credentials a role's `MaxSessionDuration`; the number is a decision.
4. **Where `iam.json` lives and how it is backed up**: a second volume or a `subPath` of the same one, 0600, in the
   same kopia snapshot; it is a key store.
5. **The migration**: every writer re-minted as an IAM user with a policy, in one window, with the hov1 pipeline
   writing the new Secrets, and the admin-API methods of the extension retired or kept for hov1 only, since hov1
   stays on internal IAM.

## Not in this plan

- Zulip itself: its plan brings its database partition and its two buckets.
- Moving the backup target off hov1, or a second copy at the provider's object storage (020 says how).
- Virtual-host-style bucket addressing and a wildcard certificate under `dvkt.no`.
- A name for the hov1 endpoint, `s3.hov1.dvkt.no`, which `backup/hov1/README.md` defers until the address changes.
  Step 1's zone work makes it one line when that day comes.
- Keystone, Forgejo or Zulip federating to Zitadel: each is its own plan, after 015's shape is proven on Kubernetes.
